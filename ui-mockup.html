Two front doors, one core

The MCP server isn't a bonus feature — it's the interface you'll use most. You're already in a Claude session when you find a repo; the URL should never have to leave the chat.

The constraint that keeps it simple: MCP tools and HTTP endpoints call the same functions. One core module, two thin adapters. Let them drift and you own two products.

Stack

  • TypeScript, one package, no UI framework. core/ (SQLite + the six operations above), mcp/ and web/ as thin adapters. Vite for the build. Three folders.
  • SQLite, four owned fields — why_i_want_it, state, retire_reason, tags, plus favorite. Everything else derived from disk, package managers, agent configs, atom feeds.
  • Single-user, localhost, no auth. Open source from commit one, MIT.
  • Global settings, one screen — clone path (D:\dev\tools), auto-update default (off), which agents register_mcp targets, which catalogs Browse queries. Per-row overrides where it matters.
  • It registers itself. First run: OSource-Manager writes its own MCP entry into your agents — using the same register_mcp everything else uses. If that's broken, you find out immediately.
  • Local only. No cloud trial, no hosted mode, no daemon. Containers run on your machine or they don't run.
  • Scale: table for the hot set, CtrlK past a few hundred rows. Virtualize only when a real row count makes it lag.
Skipped: auth, multi-user, hosted mode, notifications, daemon, dependency tracking inside repos, container management past trial + teardown. Open source means someone else can add what they need — you don't pre-build it for them.

Browse — other people's shelves

Manage is your stuff. Browse is everyone else's — queried live, never mirrored. Track is the bridge: it costs one row and no disk, so tracking a whole category is cheap. Cloning is the deliberate second step.

What this does not build

Containers are the right primitive — and container management is a solved, crowded space. Building another one would be the Higgsfield mistake a second time.

Backend

  • Discovery is derived, never typed. Walk the tools folder for .git; ask each package manager (npm ls -g, pipx list, cargo install --list, scoop list, winget list); read the three skills directories; docker ps -a for trials.
  • You own four fields. why_i_want_it, state, retire_reason, custom_tags. Everything else is read from disk, configs, or GitHub. This is what stops it becoming tool #61.
  • “Serving ×N” is counted, not recorded — grep each agent's config for the server name. Register or unregister anywhere and the count self-corrects.
  • The AI part is generating the run command — read compose/Dockerfile/README, pick a free port, set shm_size, prefer named volumes, label for teardown. That's the piece Portainer can't do and you'd get wrong by hand.
  • Upstream = releases atom feed, one fetch per repo on open and on refresh. Timestamp to the second. No daemon.
  • MCP registration: in Docker's catalog → hand to MCP Toolkit. Not in it → write the agent's config directly, backing up the file first. Dry run shows the diff.
  • Stack: one Python file, SQLite, stdlib http.server. No framework, no auth, localhost.
Skipped: notifications, daemon, auth, multi-machine sync, dependency tracking inside repos, container management beyond trial + teardown. Add release notifications when you've actually missed one that mattered.
